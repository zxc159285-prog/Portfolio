PROJECT 01 · 03 · FILE TRANSACTION INTEGRITY
[기능 3] 레시피 CRUD & 데이터 무결성 보장 파일 트랜잭션 조종현 100% 전담

@Transactional 내 DB CASCADE 전 파일 metadata 메모리 선 복사 및 2단계 물리 삭제.

기능 설명 & 설계 의도
  • 문제 상황: 게시글 삭제 시 DB row만 지워지고 서버 디스크 파일이 남아 용량이 누수되는 현상.
  • 메커니즘: @Transactional 범위 내에서 DB Cascade 삭제 전 삭제 파일 리스트를 자바 메모리에 선 복사.
  • 무결성 보장: DB 삭제 성공(result > 0) 시에만 FileManager.fileDelete()를 실행하여 물리 파일 완전 제거.
실제 백엔드 소스코드 (MyRecipeService.java)
@Transactional
public int delete(MyRecipeDTO myRecipeDTO) throws Exception {
    // 1. DB CASCADE 전 파일 metadata 메모리 백업
    MyRecipeDTO detail = myRecipeMapper.detail(myRecipeDTO);
    List<RecipeFileDTO> targetFile = detail.getRecipeFileDTO();

    // 2. DB 삭제 쿼리 실행
    int result = myRecipeMapper.delete(myRecipeDTO);

    // 3. DB 삭제 성공시에만 실제 서버 물리 파일 삭제
    if (result > 0 && targetFile != null) {
        for (RecipeFileDTO fileDTO : targetFile) {
            fileManager.fileDelete("myrecipe", fileDTO);
        }
    }
    return result;
}

PROJECT 01 · 04 · COMMON PAGER UTILITY
[기능 4] 백엔드 공통 Pager 유틸리티 & 0건 방어 로직 조종현 100% 전담

DRY 원칙 준수 페이징 엔진, Offset/Limit 및 페이지 블록 자동 계산, 0건 방어막 구현.

기능 설명 & 설계 의도
  • DRY 수칙 준수 Pager.java: Offset/Limit(`startNum`), 페이지 당 개수, 블록 계산을 단일 캡슐화 유틸리티로 모듈화.
  • 0건 경계조건 방어막: 데이터가 0건일 때 인덱스 예외나 레이아웃이 깨지지 않도록 totalCount == 0 방어막 탑재.
  • 재사용성: 레시피 목록, 요리 기록, 장바구니 등 모든 컨트롤러에서 일관되게 적용.
실제 백엔드 소스코드 (Pager.java)
public void makeBlock(Long totalCount) {
    Long perBlock = 5L;
    // 0건일 경우 방어 로직 (1페이지 고정)
    if(totalCount == 0) {
        perBlock = 1L; next = false; pre = false;
    }
    Long totalPage = (totalCount % getPerPage() == 0) ? 
        totalCount / getPerPage() : (totalCount / getPerPage()) + 1;
    Long curBlock = (getPage() % perBlock == 0) ? 
        getPage() / perBlock : (getPage() / perBlock) + 1;

    start = (curBlock - 1) * perBlock + 1;
    end = curBlock * perBlock;
    if(curBlock == totalBlock) { end = totalPage; next = false; }
}

주요 백엔드 설계 및 검증 Q&A

Q. Gemini AI 연동 시 응답 지연 문제는 어떻게 극복했나요?

A. Spring @Scheduled 배치 작업으로 식사시간 직전에 메뉴를 사전 생성해 DB에 저장 및 캐싱함으로써, 사용자 요청 시 실시간 지연 없이 10ms 이내로 즉각 응답하도록 처리했습니다.

Q. Pager 유틸리티의 설계 이점은 무엇인가요?

A. 모든 게시판의 페이징 파라미터 계산을 캡슐화하고 totalCount 0건 방어막을 탑재하여 DRY 수칙을 완벽히 준수했습니다.

@Autowired
private BCryptPasswordEncoder passwordEncoder;

public int update(MemberDTO memberDTO) throws Exception {
    if (memberDTO.getPassword() == null || memberDTO.getPassword().trim().isEmpty()) {
        return -1; 
    }
    if (!memberDTO.getPassword().equals(memberDTO.getPasswordCheck())) {
        return -2; // 비밀번호 불일치 에러 플래그
    }
    // BCrypt 평문 해시 암호문 치환
    String hashedPassword = passwordEncoder.encode(memberDTO.getPassword());
    memberDTO.setPassword(hashedPassword);

    return memberMapper.update(memberDTO);
}

@Transactional
public int sendCoupon(CouponDTO couponDTO) throws Exception {
    // 미사용 동일 쿠폰 보유 여부 중복 방어
    int dupCount = couponMapper.checkDuplicateUnused(
        couponDTO.getToId(), couponDTO.getCouponNum()
    );
    if (dupCount > 0) {
        throw new IllegalArgumentException("이미 미사용 동일 쿠폰을 보유 중입니다.");
    }
    int result = couponMapper.sendCoupon(couponDTO);
    if (result > 0) {
        couponMapper.sendCount(couponDTO.getCouponNum());
        alarmService.sendAlarm(
            couponDTO.getToId(), couponDTO.getFromId(),
            "새로운 쿠폰 도착: " + couponDTO.getCouponName(),
            "/fitc/mypage/coupon", "COUPON"
        );
    }
    return result;
}

private SseEmitter subscribe(String username) throws Exception {
    // 30분 만료 시간을 가진 새로운 실시간 전선 객체 생성
    SseEmitter emitter = new SseEmitter(DEFAULT_TIMEOUT);

    emitter.onCompletion(() -> alarmRepository.remove(username, emitter));
    emitter.onTimeout(() -> alarmRepository.remove(username, emitter));
    emitter.onError(e -> alarmRepository.remove(username, emitter));

    // 503 Gateway Timeout 방지 최초 핑 이벤트 전송
    emitter.send(SseEmitter.event().name("connect").data("연결 완료"));
    alarmRepository.save(username, emitter);
    return emitter;
}

문제 상황 (단일 경로 추적의 한계)

기존 내비게이션은 '하나의 선'만 추적합니다. 하지만 듀얼 라우팅 환경에서 기사님이 '빨간 선(숏컷)'이 위험해 보여서 '파란 선(카카오 안전로)'을 골라 탔음에도 불구하고, 앱은 "빨간 선에서 멀어졌다!"며 경로 이탈 경고를 울리는 논리적 버그가 발생했습니다.

해결 방안

내 위치에서 '빨간 선'과 '파란 선'까지의 직교 거리를 각각 계산한 뒤, 둘 중 하나라도 20m 이내에 있다면 정상 주행으로 인정(Math.min)하는 다중 센서망을 구축했습니다. 일반 자동차(40m)보다 2배 예민한 20m 기준을 적용해 골목길 엇나감에 즉각 반응합니다.

[T/S 3] BRouter 해시 검증 우회 & 극단적 Cost 페널티 튜닝

오픈소스 API의 폐쇄적 보안 정책(MD5 Hash)을 뚫어내고, 오토바이만의 극한 숏컷(계단/일방통행 배제)을 뽑아내는 프로파일 튜닝

BRouter 보안 Hash 우회

BRouter API는 커스텀 프로파일(Custom Profile)을 요청할 때 파라미터 변조를 막기 위해 독자적인 MD5 Hash 파라미터를 요구했습니다.

하지만 프론트엔드 단독 환경에서는 백엔드 프록시 없이 이를 뚫어야 했고, 오픈소스 코드를 역엔지니어링하여 JavaScript 환경에서 동일한 해시를 생성하는 알고리즘(String.prototype.replace / unescape / encodeURIComponent 콤보)을 이식해 보안 검증을 완벽히 우회했습니다.

// 오토바이에게 치명적인 도로(계단, 보행자도로)를 완전히 배제하는 페널티 튜닝 (profile)
const customProfile = `
  assign initialcost = 0
  assign defaultaccess = true
  assign nodeaccesspenalty = 0
  assign turninstructionmode = 1
  ---
  assign costfactor
    switch or highway=steps highway=pedestrian 10000
    switch highway=motorway 10000
    1
`;
